# Где хранить память и где работает MCP

**Текущая схема хранения:** рабочие SQLite, оригиналы и Markdown остаются на сервере владельца.
В S3 находятся оперативные вложения и отдельное зашифрованное хранилище restic, тоже с байтами
оригиналов. Между снимками restic одинаковые блоки не копируются повторно. Это две независимые
копии оригиналов, поэтому прогноз учитывает обе. Локальные staging/cache тоже занимают место.
`storage_report` показывает составляющие; `refresh_s3=true` отдельно учитывает старые версии
объектов. `forecast_import` оценивает пик места перед выбранной выгрузкой, без гарантии цены.
Настройки, резервирование, восстановление и папки проектов: [подробная инструкция](recovery-and-folders.md).

Для нового пользователя начни с [onboarding.md](onboarding.md). Установка Cloud.ru preview
включает ВМ, S3/restic и HTTPS/OAuth через Container Apps без покупки домена; данные остаются
на ВМ. [Установщик](deployment.md) также поддерживает свой Linux-сервер по SSH.
Ниже — выбор размещения и ручные локальные/серверные способы. HTTPS для произвольного
своего сервера пока требует отдельной административной настройки.

Эту инструкцию агент использует при первом подключении, выборе хранилища или переносе.
Объясняй её на языке пользователя. Если размещение уже выбрано, используй этот выбор.
Если MCP уже подключён, сначала прочитай `memory_status`: `storage.server_directory` относится
к машине сервера, а не обязательно к компьютеру пользователя. Страна автоматически не определяется.

## Выбор перед первым импортом

1. **Есть общая память?** Подключи её адрес или существующую локальную папку. Не создавай новую
   пустую память только потому, что пользователь установил скилл в ещё одного агента.
2. **Новая память:** для первого теста или работы на одном компьютере предложи локальную папку.
   Для нескольких компьютеров и серверных агентов — один принадлежащий пользователю сервер.
   Если выбор ещё не сделан, уточни эти два варианта и требуемую страну хранения.
3. Объясни, где будут база, исходные материалы, вики и резервные копии; кто запускает MCP;
   какие данные подключённая модель получает при чтении. Не начинай импорт, пока место не выбрано.
4. После подключения проверь статус и идентификатор памяти. Объясни доступные источники,
   затем выполни выбранный пользователем импорт. Не требуй повторного согласия на уже выбранный объём.

## Что поддерживается сейчас

| Вариант | Применение | Текущее состояние |
|---|---|---|
| Папка на своём компьютере | Рабочая память и локальный MCP | Реализовано |
| Диск своего Linux/Windows-сервера | Общая память нескольких своих агентов | Реализовано; владелец настраивает запуск и доступ |
| Cloud.ru | Общая память с HTTPS/OAuth без своего домена | Управляемый установщик в ветке release/1.0; стоимость ресурсов оплачивает владелец |
| Другой VPS/облачная ВМ | Сервер в выбранной стране | Установщик для своего Linux-сервера через SSH; HTTPS настраивается отдельно |
| S3, в том числе российский | Оригиналы вложений и резервные архивы | Верификация скачиванием; рабочая SQLite и локальные оригиналы остаются на диске |
| Приватный Git-репозиторий | Необязательные снимки выбранных Markdown-страниц | Автосинхронизации нет; не является рабочей базой |
| PostgreSQL | Возможный будущий вариант для большого сервиса | Не реализовано |

Рабочая папка содержит `context.sqlite3`, сохранённые байты исходных файлов в `originals`, `vault` с Markdown и служебные данные. В базе находятся также редакции,
задачи, граф и версии вики. Одна только папка Markdown или экспорт JSONL не заменяет полную копию.
Расположение задаётся `--home`, либо `PC_HOME`; по умолчанию — `~/.portable-context` на машине процесса.

**Приватный GitHub не выбирай для требования «хранить только в России».** Видимость репозитория
не задаёт российский регион хранения. Для личных Markdown-снимков Git может быть полезен,
если пользователь принимает место размещения, но удаление файла не удаляет его старые версии
из истории: [документация GitHub](https://docs.github.com/en/repositories/working-with-files/managing-files/deleting-files-in-a-repository).
Публичный репозиторий проекта хранит код; личную память держи отдельно.

## Локальный запуск: без покупки хостинга

Нужны Git и Python 3.11+ с SQLite FTS5. Команды выполняются на компьютере владельца памяти.
Клонирование нужно один раз; если репозиторий уже скачан, начни в его каталоге.

```sh
git clone https://github.com/vlemutov/portable-context.git
cd portable-context
python -m venv .venv
```

Windows PowerShell, установка и создание отдельной папки:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[mcp]"
.\.venv\Scripts\portable-context.exe --home "$env:USERPROFILE\PortableContextData\memory" init
.\.venv\Scripts\portable-context.exe --home "$env:USERPROFILE\PortableContextData\memory" status
```

Linux/macOS, установка и создание папки с доступом только владельцу:

```sh
.venv/bin/python -m pip install -e '.[mcp]'
mkdir -p "$HOME/.local/share/portable-context"
chmod 700 "$HOME/.local/share/portable-context"
.venv/bin/portable-context --home "$HOME/.local/share/portable-context" init
.venv/bin/portable-context --home "$HOME/.local/share/portable-context" status
```

`init` создаёт пустое хранилище, но ничего не импортирует и не запускает фоновую службу.
В приложении агента настрой MCP: команда — **абсолютный путь** к установленному
`portable-context.exe` / `portable-context`, аргументы — `--home`, абсолютный путь к памяти, `mcp`.
В этих настройках не рассчитывай на раскрытие `~` или переменных оболочки самим приложением.

Пример общей формы конфигурации для клиента со stdio (имена каталогов замени своими):

```json
{
  "mcpServers": {
    "portable-context": {
      "command": "C:\\tools\\portable-context\\.venv\\Scripts\\portable-context.exe",
      "args": ["--home", "C:\\Users\\YOUR_USER\\PortableContextData\\memory", "mcp"]
    }
  }
}
```

Формат настроек зависит от приложения; этот JSON не универсален. Установи **всю папку**
`skills/portable-context` в поддерживаемый приложением каталог скиллов, включая `references`.
Если скиллы не поддерживаются, агенту доступны MCP-ресурсы `portable-context://setup` и
`portable-context://guide`. Вызови `memory_status` и проверь выбранную папку до первого импорта.

В режиме stdio приложение запускает Python-процесс MCP на этой машине. После завершения процесса
память остаётся на диске. Другое приложение на том же компьютере может использовать ту же папку.
Веб-приложение не получает доступ к локальному процессу автоматически: нужен поддерживаемый
им удалённый MCP или предусмотренный этим приложением локальный мост.

## Свой сервер, включая размещение в России

Для пользователя с несколькими серверными агентами рекомендуемая схема:

```text
Локальные и серверные агенты → защищённый доступ → один MCP + рабочий диск
                                                        ↓
                                        отдельные резервные копии
```

Варианты инфраструктуры, проверены по документации 1 ноября 2026:

- **Yandex Cloud:** создать ВМ в регионе Russia (`ru-central1`), рабочую папку разместить
  на её диске; при необходимости создать отдельный закрытый Object Storage bucket в России
  для резервных архивов. У провайдера есть и другие страны, поэтому выбирать нужно именно регион.
  [Регионы](https://yandex.cloud/en/docs/overview/concepts/region),
  [создание ВМ](https://yandex.cloud/ru/docs/compute/operations/vm-create/create-linux-vm),
  [создание бакета](https://yandex.cloud/ru/docs/storage/operations/buckets/create).
- **Selectel:** создать облачный сервер в российской локации; резервные копии при необходимости
  размещать в S3 российской локации. Страну сервера и бакета проверяй отдельно: у провайдера
  есть инфраструктура в нескольких странах.
  [Локации](https://docs.selectel.ru/infrastructure/locations/),
  [серверы](https://selectel.ru/services/cloud/servers/),
  [S3](https://selectel.ru/services/cloud/storage/).
- **Собственный компьютер/сервер в России:** тот же способ без облачного провайдера.
  NAS может хранить резервные копии; рабочая база должна обслуживаться процессом на той же
  машине с подходящим локальным диском, а не открываться несколькими компьютерами через SMB/NFS.

Это варианты размещения, а не готовые кнопки подключения облачных аккаунтов в Portable Context.
Хранилище S3 сохраняет объекты, но не исполняет MCP. Покупка одного бакета не заменяет сервер.

### Ручной сервер со статическим токеном

Это расширенный альтернативный вариант. Для обычной установки используй [deployment.md](deployment.md),
для подключения существующей — [connection.md](connection.md).
Последовательность ручного серверного запуска:

1. Создать сервер в нужной стране с постоянным диском. Использовать отдельного непривилегированного
   пользователя для процесса; установить Python и проект как в локальном примере.
2. Выбрать приватный каталог на диске сервера, выполнить `init`. Оставить одну рабочую копию памяти.
3. Для HTTP задать случайный `PC_MCP_TOKEN` (не менее 24 символов) в окружении сервера.
   Хранить его в защищённых настройках службы и клиента, не в репозитории и не в разговоре.
   Пример для временного запуска из Linux-shell без вывода токена:

   ```sh
   export PC_MCP_TOKEN="$(.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))')"
   .venv/bin/portable-context --home "$HOME/.local/share/portable-context" mcp --transport streamable-http --port 8766
   ```

   Этот пример работает, пока жив процесс; переменную потребуется безопасно перенести в клиент.
   Для постоянной работы настрой systemd или другой менеджер служб с тем же каталогом и токеном,
   перезапуском после сбоя и загрузки ОС. Программа сама службу не устанавливает.
4. MCP слушает только `127.0.0.1:8766`, путь `/mcp`. Для клиента с SSH можно открыть туннель:

   ```sh
   ssh -N -L 18766:127.0.0.1:8766 user@your-server
   ```

   На компьютере с этим туннелем адрес MCP — `http://127.0.0.1:18766/mcp`;
   заголовок — `Authorization: Bearer <ваш токен>`. Туннель должен оставаться открытым.
   Для клиентов без SSH нужен HTTPS-прокси к loopback-сервису. Не публикуй открытый HTTP с токеном.
5. Проверить поддержку транспорта и авторизации в каждом клиенте. Веб-клиенты, требующие OAuth,
   не подключатся к этому примеру только со статическим токеном. Управляемый Cloud.ru preview
   отдельно устанавливает Pocket ID/OAuth; другие варианты требуют настройки. Нельзя обещать, что одного
   URL и токена хватит любому Claude/GPT/Gemini или агенту.
6. Подключить скилл и сравнить `workspace_id` через `memory_status` у клиентов. При этом они
   должны обращаться к **одному рабочему экземпляру**, а не к двум восстановленным копиям
   с одинаковым ID. Папки не синхронизируются по идентификатору.
7. Подготовить резервное копирование, затем импортировать выбранные данные. Разрешённый каталог
   исходных архивов задаётся отдельно через `mcp --source-root`; клиентский путь не становится
   серверным автоматически.

Один экземпляр предназначен для одного владельца и его доверенных агентов: отдельных прав
доступа пользователей внутри общей базы нет. Другому человеку, скачавшему репозиторий, нужны
свои папка/сервер, настройки и токен. Он не подключается к серверу автора проекта автоматически.

## Резервные копии, Obsidian и перенос

Не синхронизируй работающий `context.sqlite3` через Git, Яндекс Диск, S3-mount или сетевую папку.
SQLite WAL требует, чтобы работающие с базой процессы находились на одной машине:
[документация SQLite](https://sqlite.org/wal.html). Для удалённых агентов используй MCP.

Простой надёжный порядок резервирования:

1. Остановить все процессы, записывающие в эту память: MCP, импорт, сборщики; на время копии
   остановить и ручные правки Markdown. Сохранить очереди доставки отдельно, если они используются.
2. Скопировать **всю папку памяти**, включая существующие SQLite WAL-файлы, originals и vault,
   в отдельный каталог резервной копии. Не удалять служебные SQLite-файлы вручную.
3. Возобновить работу. Полученную неподвижную копию архивировать и при необходимости шифровать
   внешним инструментом. Отдельного шифрования архивов пока нет; серверный установщик настраивает cron.
4. Загрузить архив в закрытый бакет выбранного региона или на другой диск. Ограничить доступ
   отдельной учётной записью; ключ восстановления хранить отдельно от архива.
5. Периодически восстанавливать в тестовую отдельную папку, запускать `status` и `lint`, проверять
   известный разговор и страницу вики. Не подключать сборщики к тестовой копии.

Для переноса на сервер используй тот же порядок копирования, затем поменяй настройки клиентов
на новый сервер и проверь ID и содержимое. Старую копию оставь отключённой от записи.
Для онлайн-копий используй `python -m portable_context.backup`: база копируется через SQLite backup API,
исходники проверяются по хешам; ручные Markdown-правки сохраняются отдельно для сверки при восстановлении.
Полный порядок и ограничения описаны в [инструкции развёртывания](deployment.md).

На локальной машине Obsidian открывает `vault`. При серверном хранении можно скачивать его
снимок для чтения; это не синхронизация всей памяти. Двусторонний обмен удалёнными ручными
правками Markdown сейчас не автоматизирован. Правки через MCP проходят проверку версий.

## Хранение в России и обработка моделью — разные настройки

Российские сервер и резервный бакет определяют размещение этих копий. Когда внешний облачный
агент читает память через MCP, полученные фрагменты входят в его контекст и могут обрабатываться
за пределами России. Для требования «все данные остаются в России» также нужны локальная или
подходящая российская модель и проверенное размещение прокси, логов, резервных копий и будущих
сервисов эмбеддингов. Само ядро Portable Context внешнюю модель не вызывает и эмбеддинги не строит.
Не обещай соблюдение требований локализации только на основании названия облачного провайдера.
