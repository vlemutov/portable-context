# Развёртывание у владельца: cloud.ru или свой сервер

Это инструкция для агента, сопровождающего человека от установки до готовой памяти.
Человек владеет ресурсами и платит провайдеру напрямую. Общего сервиса Portable Context нет.
Автоматический серверный путь рассчитан на Ubuntu 24.04 / Linux с Python 3.11+, SSH и cron.
Клиентский установщик работает в Windows, macOS и Linux; для некоторых архитектур нет
бинарного Terraform-провайдера cloud.ru — `bootstrap` явно сообщит об этом.

## Как вести пользователя

1. Определи, создаётся новая память или подключается существующая. Используй уже выбранный
   вариант: **cloud.ru** или **свой сервер**. Не повторяй вопросы, на которые человек ответил.
2. Работай инструментами терминала, когда они доступны. Не перекладывай на человека составление
   JSON, выбор идентификаторов образов и настройки Terraform. Веб-агент без терминала ведёт
   по тем же шагам, но выполнение команд потребуется на компьютере пользователя.
3. Используй официальный репозиторий `https://github.com/vlemutov/portable-context`, сохрани
   выбранный commit. Если скачан только скилл, получи полный репозиторий: установщик находится
   в `deploy/setup.py`. Не считай появление SKILL.md установкой программы или MCP.
4. Выбери **постоянную приватную папку состояния вне репозитория**. На последующих шагах и при
   повторах используй её же. Потеря Terraform state и SSH-ключа не исправляется созданием новой ВМ.
5. Объясни человеку конкретные платные ресурсы и текущую стоимость до применения плана.
   Установщик сам цены не вычисляет. Используй актуальный калькулятор для выбранной конфигурации,
   учти диск, IPv4, S3, операции и трафик; не обещай бесплатное размещение по умолчанию.
6. После развёртывания выполни `install` и `check`. Не сообщай «готово», пока не проверены
   соединение MCP и резервирование. Только после этого переходи к выбранному импорту.

## cloud.ru: что человек делает один раз

- Создаёт аккаунт, подключает оплату и проект, активирует Compute/VPC и Object Storage.
- Предоставляет установщику ключ доступа для развёртывания в **своём проекте**. Для первой
  версии рекомендуем отдельный проект и сервисный аккаунт администратора этого проекта:
  установщик создаёт сеть, ВМ, бакет и отдельный сервисный аккаунт резервирования с ролями.
  Не проси доступ администратора всей организации.
- Сообщает Project ID и Tenant ID Object Storage. Эти идентификаторы не секретные. Остальные
  идентификаторы агент получает через `catalog`; не нужно вручную создавать сеть, ВМ и бакет.
- Ключ вводит в своём терминале через `credentials` или задаёт `AUTH_KEY_ID` / `AUTH_SECRET`
  в локальном окружении. Не проси прислать секрет в чат и не печатай содержимое файлов ключей.

Официальные инструкции: [ключ доступа](https://cloud.ru/docs/console_api/ug/topics/guides__api_key),
[Tenant ID и S3-аутентификация](https://cloud.ru/docs/s3e/ug/topics/api__api-key),
[роли Object Storage](https://cloud.ru/docs/s3e/ug/topics/security__role).
Сервисный ключ развёртывания остаётся локально; на ВМ передаётся только отдельный ключ резервирования.
Terraform state содержит этот ключ и должен храниться приватно вместе с SSH-ключом.

## Команды cloud.ru

Ниже `PRIVATE_STATE` — абсолютный путь к выбранной приватной папке, а команды запускаются
из полного репозитория. Агент подставляет реальные пути. Python 3.11+ и OpenSSH нужны на клиенте.

```sh
python deploy/setup.py --state PRIVATE_STATE init --mode cloudru
python deploy/setup.py --state PRIVATE_STATE doctor
python deploy/setup.py --state PRIVATE_STATE bootstrap
python deploy/setup.py --state PRIVATE_STATE credentials
python deploy/setup.py --state PRIVATE_STATE catalog --project-id PROJECT_UUID
```

`bootstrap` скачивает Terraform 1.13.5 и официальный провайдер cloud.ru 2.1.6, проверяет SHA-256
и устанавливает **внутрь папки состояния**. Глобальный PATH и пользовательский terraform.rc не меняются.
Контрольные суммы провайдера зафиксированы из официального GitHub release. При недоступности
GitHub можно использовать официальный cloud.ru mirror с установленным Terraform; инструкция
провайдера: [быстрый старт](https://cloud.ru/docs/terraform-evolution/ug/topics/quickstart).

`catalog` выполняет только чтение: возвращает образы, конфигурации и зоны, сохраняет `catalog.json`.
Агент выбирает доступный образ Ubuntu 24.04 без GPU, небольшую подходящую конфигурацию и зону,
проверяет минимум CPU/RAM/диска у образа. Если список неоднозначен — показывает подходящие варианты.
Не подставляй UUID из примеров или устаревшего разговора. Провайдер может ограничивать каталог;
не выдавай полученный список за доказательство отсутствия других конфигураций.

Агент создаёт вне репозитория JSON с **несекретными** параметрами:

```json
{
  "project_id": "PROJECT_UUID",
  "tenant_id": "TENANT_UUID",
  "zone": "ZONE_FROM_CATALOG",
  "image_id": "UBUNTU_24_04_IMAGE_UUID",
  "flavor": "FLAVOR_FROM_CATALOG",
  "ssh_cidr": "YOUR_PUBLIC_IPV4/32",
  "disk_gb": 40
}
```

Адрес для SSH — публичный адрес выхода **того компьютера, где будет работать MCP-клиент**.
Можно использовать подходящую доверенную подсеть; `0.0.0.0/0` установщик не принимает.
Имя бакета и установки генерируется один раз автоматически. Затем:

```sh
python deploy/setup.py --state PRIVATE_STATE configure --file OPTIONS_JSON
python deploy/setup.py --state PRIVATE_STATE plan
```

План создаёт VPC, подсеть, правила сети, интерфейс, IPv4, защищённый от удаления SSD, ВМ,
закрытый версионируемый бакет и отдельный ключ с правами чтения/записи **на этот бакет**.
Рабочая SQLite и Markdown находятся на постоянном загрузочном диске ВМ. Диск не форматируется
установщиком при повторном запуске. SSH открыт только для выбранного CIDR; HTTP MCP наружу не открыт.
Бакет должен вернуть UUID для назначения прав; если это не поддерживается аккаунтом/API,
остановись на диагностике и не расширяй права ключа на весь проект автоматически.

Покажи пользователю изменения из `plan-review.json` и оценку расходов. После согласования
конкретного плана (либо в пределах ранее согласованных ресурсов и бюджета):

```sh
python deploy/setup.py --state PRIVATE_STATE apply --approve-plan PLAN_SHA256
python deploy/setup.py --state PRIVATE_STATE install
python deploy/setup.py --state PRIVATE_STATE check
```

`apply` принимает только точный просмотренный план; изменение параметров требует нового `plan`.
Удаление/замена ресурсов отклоняется. После ошибки не удаляй state, не меняй имя установки и
не создавай второй проект: повтори `plan` с тем же состоянием или `install`, если ресурсы уже созданы.
Сетевые/квотные ошибки cloud.ru и особенности конкретного образа проверяются на реальном аккаунте;
локальные тесты и Terraform validate не являются испытанием платного развёртывания.

## Как агент подключается к готовой памяти

`install` передаёт текущий исходный код по SSH, ставит его в отдельное виртуальное окружение,
создаёт приватную память и каталог импортов. Повторная установка сохраняет память и идентификатор.
Для одной учётной записи Linux предусмотрена одна установка в `~/.local/share/portable-context-server`.
Код лежит в версиях `releases`, рабочая версия указана ссылкой `current`.

Файл `PRIVATE_STATE/client-config.json` содержит готовый stdio MCP, запускающий `ssh`.
**MCP исполняется на сервере**, а SSH переносит протокол между ним и приложением. Домен, публичный
HTTP, ручной запуск туннеля и OAuth для этого пути не требуются. Процесс запускается при подключении
агента; память хранится постоянно, а резервирование выполняется независимо через cron.

Агент объединяет запись с существующей конфигурацией своего приложения, сохраняя остальные MCP.
Для приложений с TOML преобразует `command` и `args` в их формат. Если настройки можно менять только
через интерфейс, выдаёт готовые значения. Проверка `check` использует MCP SDK: локально установи
`python -m pip install -e '.[mcp]'` в виртуальное окружение и запусти проверку его Python.
Она сверяет `workspace_id` с установленной памятью. Первое SSH-подключение использует TOFU
(`accept-new`) и сохраняет known_hosts; изменившийся ключ сервера отклоняется.

Для второго своего агента настрой доступ к **той же ВМ и памяти**. На другой машине нужно настроить
её собственный SSH-ключ и добавить её адрес в разрешённую сеть; ключи не пересылаются через чат.
Приложению нужен доступ к SSH-ключу или SSH-agent. Не обещай работу этого способа в веб-клиенте без
локального исполнителя. HTTPS-вариант остаётся отдельной ручной настройкой из инструкции хранения.

## Альтернатива: существующий, в том числе домашний, сервер

Агент сначала проверяет ОС, Python, SSH, доступное место, возможность установки зависимостей,
адрес сервера и способ доступа из нужных сетей. Для домашнего сервера за NAT подойдет локальная
сеть или уже настроенный VPN; установщик сам роутер и VPN не перенастраивает.

На Ubuntu 24.04 при отсутствии зависимостей агент помогает выполнить:

```sh
sudo apt-get update
sudo apt-get install python3 python3-venv python3-pip openssh-server cron
sudo systemctl enable --now ssh cron
```

Используй отдельную непривилегированную Linux-учётную запись и уже работающий вход по SSH-ключу.
Для других ОС проведи пользователя через установку Python 3.11+/OpenSSH/cron или подготовку Linux-ВМ.
Не обещай автоматический bootstrap на произвольной ОС. Затем на клиенте:

```sh
python deploy/setup.py --state PRIVATE_STATE init --mode server
python deploy/setup.py --state PRIVATE_STATE configure --file SERVER_OPTIONS_JSON
python deploy/setup.py --state PRIVATE_STATE install
python deploy/setup.py --state PRIVATE_STATE check
```

Пример `SERVER_OPTIONS_JSON`:

```json
{
  "host": "192.168.1.50",
  "ssh_user": "memory",
  "ssh_port": 22,
  "identity_file": "/absolute/path/to/private/ssh-key",
  "schedule_backup": true
}
```

На Windows в JSON используй `C:/Users/...` или экранированные обратные слеши. Terraform и аккаунт
cloud.ru для этого варианта не нужны. По умолчанию копии локальные; они не защищают от потери диска.
Для имеющегося S3 агент помогает настроить приватный `PRIVATE_STATE/backup-config.json` с полями
`endpoint` (HTTPS), `region`, `bucket`, `access_key`, `secret_key`. Секреты вводятся локально.
`install` передаст настройки по SSH и проверит загрузку, скачивание и восстановление.

## Резервирование и восстановление

Установка делает пробную копию, для cloud.ru — загружает в S3, скачивает и восстанавливает в
временную папку. Только после успешного восстановления добавляет одну ежедневную запись cron,
03:17 по времени сервера. Существующие записи cron сохраняются. Проверь, что демон cron запущен;
на домашнем сервере резервирование возможно, пока он включён. Результат последнего запуска:
`~/.local/share/portable-context-server/backup.log`.

SQLite копируется через backup API, исходники — по зафиксированным хешам из снимка.
Markdown сохраняется отдельной копией `recovered-vault`, поскольку ручные правки файлов не являются
транзакцией SQLite. При восстановлении вики строится из базы, старые заметки `vault/memory`
возвращаются, а остальные ручные правки нужно сверить с `recovered-vault`.
Внешние архивы-источники и outbox других серверов копируются отдельно. Локальные пути источников
после переноса нужно перенастроить; не возобновляй импорт по старым путям вслепую.

На сервере, из каталога `~/.local/share/portable-context-server`:

```sh
./bin/backup
./current/venv/bin/python -m portable_context.backup download --s3-config backup-config.json --key backups/NAME.zip --output /private/download.zip
./current/venv/bin/python -m portable_context.backup restore /private/download.zip --destination /private/restored-memory
./current/venv/bin/portable-context --home /private/restored-memory status
```

Восстановление разрешено только в новый каталог. Для переключения рабочей памяти останови
подключённые агенты и cron-запись этой установки, сохрани текущую папку, затем замени её проверенной
восстановленной копией и проверь ID/содержимое перед возобновлением. Не подключай агентов к двум
независимым копиям с одинаковым workspace_id.

После успешной отправки в S3 остаются последние семь локальных ZIP. При ошибке отправки копия
остаётся локально. В S3 автоматическое удаление пока не включено: объём и стоимость растут;
период хранения выбирает владелец. Архивы закрытые, но приложение не шифрует их отдельным ключом.

## Обслуживание и завершение

- При смене публичного IP клиента обнови `ssh_cidr` и просмотри новый план. При необходимости
  доступа из нескольких сетей настрой правила осознанно, не открывай SSH всему интернету автоматически.
- Не запускай новый исходный код на заполненной памяти без резервной копии. Повторный `install`
  сохраняет данные и версии программы, но обратная совместимость старого кода с новой схемой БД
  не гарантируется. Для отката используй подходящую резервную копию и соответствующую версию.
- При неудаче Terraform с захваченным выводом смотри приватный `last-error.log`; перед цитированием
  ошибки удали секреты. Не загружай state, планы, конфигурации ключей и дампы в публичные issues.
- Удаление приложения не прекращает облачные начисления. Универсальной кнопки `destroy` в
  установщике нет. Для закрытия установки сначала проверь внешний бэкап, отключи клиентов/cron,
  затем удали нужные ресурсы осознанно. `prevent_destroy` защищает диск, ВМ и бакет; это защита
  от случайности, а не запрет владельцу удалить свои ресурсы после проверки.
- Локальные ключи развёртывания можно отозвать после настройки. Для изменений инфраструктуры
  потребуется снова предоставить доступ. Резервирование продолжит работать со своим ключом.
