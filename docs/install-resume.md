# Продолжение установки: 1.0-preview.5

Используйте полный checkout одного проверенного commit. Команды выполняет агент в окружении
Python 3.11+ с `.[mcp,deployment]`. `PRIVATE_STATE` — прежняя приватная папка вне checkout.
Не запускайте `init`, не создавайте замену ВМ/памяти и не удаляйте intent после сетевой ошибки.

Для `mode=timeweb` используйте [маршрут Timeweb](timeweb-install.md#ожидание-и-продолжение).
Общие команды — `install-status` и повторный `install --https`. Команды Cloud.ru network/quota
ниже не являются диагностикой Timeweb. Потерянный ответ создания обрабатывается через
`timeweb-reconcile`, не через новый state или повторное создание ресурса.

## Проверка и продолжение

```text
python deploy/setup.py --state PRIVATE_STATE install-status
python deploy/network.py --state PRIVATE_STATE inspect --scope cloud
python deploy/network.py --state PRIVATE_STATE inspect --scope server
python deploy/setup.py --state PRIVATE_STATE quota-check
python deploy/setup.py --state PRIVATE_STATE install --https
```

Сначала сверить project ID и workspace с прежним отчётом. `install-status` читает только локальные
receipts: это не доказательство текущего здоровья сервера. Завершённые registry/image stages
повторно не создаются. На сервере проверяются workspace и релиз. Первый переход на новый commit
обновляет пакет штатным путём с резервной копией; последующие повторы того же кода пропускают
переустановку только после проверки checkpoint и живой памяти. Незавершённую миграцию другого
релиза сначала завершить исходным кодом — не удалять maintenance.json.

Если прежнее согласование HTTPS сохранено и план не менялся, повторное согласование не нужно.
Если сохранён только https-plan.json, установщик покажет его hash; сверьте расходы и доступ
с ранее согласованным планом и передайте `--approve-plan HASH`. Не выполняйте новый Terraform
plan/apply ради ошибки чтения API. При реальном изменении сети/firewall план пересматривается.

HTTP 499 распознаётся как отсутствие контейнера **только** при точном известном сообщении
`Serverless with name is not found` во время проверки имени перед CREATE. Другие 499 не обходятся.
Если CREATE уже отправлен и ответ потерян, нужны проверка ресурса и `https-reconcile` с его ID.
Повторять CREATE вслепую нельзя. Однозначно отклонённый запрос с распознанной ошибкой квоты/
мощности сохраняет незавершённый этап; после устранения ограничения можно продолжить.

## Квоты и свободные мощности

Планы и установка читают [Evolution Administration API v3](https://cloud.ru/docs/administration/ug/topics/api-ref__administration_op-v3).
`quota-report.json` содержит реальные лимиты/потребление проекта, каталога и организации,
доступные данному ключу. Ресурсы других проектов также расходуют общую квоту.
Квоты и права программа не увеличивает. Доступная квота не гарантирует физические мощности.

Агент сопоставляет **дополнительные**, ещё не созданные ресурсы плана с кодами и единицами API.
Для численной проверки создаёт несекретный JSON вида `{"КОД_ИЗ_API": 1}` и выполняет:

```text
python deploy/setup.py --state PRIVATE_STATE quota-check --phase https --requirements REQUIREMENTS_JSON
```

Не подставлять вымышленные коды или стандартные лимиты из документации. Проверка принимает
минимальный доступный остаток по всем трём уровням. `sufficient_for_selected_requirements`
относится только к переданным кодам, не ко всему плану. Неучтённые ресурсы также нужно проверить.
При `insufficient` не создавать ресурсы: объяснить ограничение и сохранить состояние для продолжения.
Для ВМ/S3 используется `--phase infrastructure`. Сопоставленные потребности сохраняются
локально и повторно проверяются перед apply/HTTPS; известный дефицит останавливает операцию.
При изменении плана или уже созданных ресурсов сопоставление теряет силу — агент рассчитывает
оставшиеся потребности заново, не учитывая уже созданное второй раз.
При 403, неполной схеме/пагинации, отсутствующих уровнях или отрицательном/неизвестном лимите —
`unknown`, а не успешная проверка. Обычный preflight без карты потребностей возвращает
`review_required`; он не блокирует установку автоматически и не доказывает достаточность квоты.
В этом случае агент проводит проверку в «Администрирование → Квоты» или помогает владельцу
прочитать значения. Не просить расширять права ключа без необходимости. Физическую нехватку
ресурсов и запрет расширения квот объяснять отдельно от сетевых таймаутов.

## Разные сетевые пути

Cloud API/S3/приватный реестр на 443 и SSH к ВМ могут требовать разных путей: напрямую или через VPN.
Не направлять все адреса мимо VPN автоматически. Сначала две отдельные диагностики выше.
Помощник включает API Container Apps, Artifact Registry, Secret Management и hostname
приватного реестра из receipts; TCP/TLS/HTTP проверяются по текущему IPv4-маршруту.
401/403 на корне HTTPS подтверждает достижимость HTTP, но не права доступа к API.
Для Linux дополнительно показываются policy rules, таблицы и route-get; fwmark конкретного VPN
может менять результат. IPv6 не проверяется и маршруты IPv6 не меняются.

`repair` создаёт новый план маршрутов. Агент проверяет **и добавления, и удаления**: смена scope
может удалить ранее управляемые исключения другого scope. Сначала выяснить, какие пути нужны
каждому каналу. Чужие/вручную добавленные маршруты помощник не присваивает. DNS и сеть
перепроверяются при apply; sudo/права администратора нужны только для согласованных изменений.
Если SSH недоступен, не повторять установку бесконечно. Проверить текущий исходящий IP и
узкое правило SSH /32; альтернативный порт SSH пока не является готовым путём установщика.

## Исправленная инициализация ВМ

Сбой SSH означает «не удалось проверить», а не неправильную архитектуру или сломанный cloud-init.
Проверки соединения имеют ограниченное число попыток. На новой облачной ВМ проверяются время,
Python/venv/ensurepip, cron и активные службы apt. Реальная ошибка cloud-init останавливает работу.
Проверка зависимостей не доказывает здоровье metadata-сервиса: при соответствующей ошибке
нужно отдельно изучить cloud-init и облачную сеть.

Если агент прочитал ошибки, восстановил зависимости на той же ВМ и cloud-init уже `done`,
но в статусе остались исторические ошибки, можно явно выполнить:

```text
python deploy/setup.py --state PRIVATE_STATE accept-cloud-init-recovery
```

Команда повторно проверяет зависимости/часы и привязывает разрешение к текущему статусу,
настройкам и boot ID. Она не исправляет ВМ и не обходит незавершённый cloud-init.
Нельзя удалять apt locks или автоматически признавать любую ошибку исторической.

## После HTTPS

Создать owner passkey, сохранить комплект восстановления отдельно, настроить точный callback
[Cursor Desktop](../skills/portable-context/references/connection.md#cursor-desktop--экспериментальный-чистый-тест)
в OAuth-клиенте этой памяти. Войти из Cursor, сверить workspace, проверить чтение/запись,
импорт сообщения и файла, повтор без дублей. Успех контейнера не равен завершённому клиентскому пути.

При новом блокере сохранить commit, install-status, этап, HTTP-код и обезличенную причину.
Не публиковать весь state, Terraform output, credentials, токены, коды входа и recovery kit.
